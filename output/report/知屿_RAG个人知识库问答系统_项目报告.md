# 摘要

针对学习笔记、技术文档和论文资料分散、依靠文件名或关键词难以定位具体知识的问题，本项目实现了一个面向个人本机使用的知识库问答原型。用户导入 PDF 或 TXT 后，系统完成文本读取、规范化清洗、递归分段和来源信息记录，通过 Embedding 接口将片段转换为向量，并使用 FAISS 建立本地索引。提问时，系统用相同的向量模型编码问题，检索相关片段，按数量、相似度和上下文预算筛选资料，再把参考资料与问题组合成 Prompt，交由兼容 Chat Completions 的模型生成流式回答。页面同时展示参考文件、PDF 页码、原文片段和相似度，方便用户核对依据。

本项目采用模块化 Python 结构。LangChain 负责文档对象、文本分段、模型适配和问答链组合；FAISS 原生接口负责向量索引；Streamlit 负责配置、导入、聊天和文档预览。系统通过文件内容哈希实现去重，通过索引配置签名避免不同模型或分段参数的索引混用，通过候选索引、临时文件和原子替换保护导入失败前的数据。离线模式使用确定性的词面哈希向量与原文摘录，便于在无密钥环境中验证流程；API 模式提供语义向量检索和大模型生成能力。

同日最近一次完整回归中，38 项自动化测试全部通过，Ruff 静态检查与依赖一致性检查通过。已完成真实 PDF 的 Embedding 导入记录；当前 API 索引快照包含 4 份文档、116 个片段，向量维度为 1024。真实问答模型的答案质量、检索准确率和响应时延仍需使用独立题集与实际服务继续评估，不能由自动化通过率直接推断。

报告依次介绍项目需求与定位、系统结构、各模块的实现原理、验证证据、关键知识点和工程注意事项，并给出复现流程、代码阅读路线及后续改进方案。项目适合作为入门级 RAG 工程实践，当前定位为单用户、小规模、本机运行的知识库问答系统。

**关键词：** 检索增强生成；文本分段；Embedding；FAISS；余弦相似度；提示词；流式问答；本地知识库

# 第一章 项目概述

## 1.1 项目背景与目标

个人学习资料通常分布在多份 PDF、笔记和技术文档中。传统文件搜索擅长查找文件名，关键词搜索擅长匹配字面表达，但用户往往只记得一个问题，未必记得原文使用的具体词语。直接向通用大模型提问，又无法保证模型了解个人资料中的细节，也难以确认答案究竟来自哪一份文档。

本项目的目标是把“打开很多文件寻找内容”转变为“提出问题并查看对应依据”。系统首先查找个人资料中的相关片段，再让模型基于这些片段组织答案。用户能够沿着引用回到文件和页码，检查回答是否有证据支持。RAG 的核心思路是把外部知识检索接入生成过程；本项目采用固定的检索后生成管线，并不复现原始研究中的联合训练机制。[R1]

本项目不训练大语言模型，也不修改现有模型的权重。导入资料主要更新外部索引，适合知识经常增补、规模较小、需要出处的个人学习场景。项目的工程重点是把文档处理、模型调用、向量检索、来源展示和异常处理连接成可运行流程。

## 1.2 功能需求与验收目标

| 功能 | 用户操作 | 系统应提供的结果 |
| --- | --- | --- |
| 文档导入 | 选择 PDF 或 TXT 并导入 | 读取内容，跳过无效文件，报告新增与重复数量 |
| 知识检索 | 输入完整的自然语言问题 | 返回相关片段，并按相似度筛选 |
| 回答生成 | 在 API 模式提问 | 基于检索资料生成中文回答，逐步展示 |
| 证据核对 | 展开参考片段 | 显示文件名、PDF 页码、片段原文和相似度 |
| 本地恢复 | 重新打开页面或重启服务 | 恢复已经保存且配置兼容的索引 |
| 资料维护 | 增量导入或显式重建 | 去重；成功重建后用目标资料集合替换旧库 |
| 会话管理 | 清空记录或导出问答 | 清除当前会话记录，或下载带参考原文的 Markdown |

验收需要区分两类目标。功能验收关注系统能否正确读入、保存、检索和展示资料；质量验收关注是否检索到真正有用的证据，以及生成结论是否受到证据支持。前者已经有自动化覆盖，后者需要另行建立标注题集和人工核对流程。

## 1.3 适用场景与实现边界

当前系统面向个人本机使用，适合课程笔记、可提取文本的论文 PDF、技术说明和小型资料集。运行时默认监听 127.0.0.1:8501。API 模式需要能够访问外部问答与向量服务；离线演示模式不需要密钥。

系统暂不提供 OCR、复杂表格理解、图片问答、用户身份认证、多人数据隔离、跨会话对话记忆、混合检索或重排序。一次提问只使用当前问题与本轮检索资料，界面显示的历史消息不会自动送入模型。因此，“继续解释上面的第二点”这类依赖前文的追问，应改写为包含主题的完整问题。

文件限制为单个 20 MB、每批 20 个，PDF 最多 500 页，知识库最多 10000 个片段。这些限制是原型的输入保护和规模约束，不代表经过压力测试的生产容量。

# 第二章 系统设计与实现

## 2.1 总体架构与数据流

系统包含建库流程和问答流程。建库负责把文件转换为可检索的向量与片段；问答负责把问题转换为查询向量，取回相关片段并生成回答。两条流程共享同一套 Embedding 配置和向量归一化规则。

<!-- FIGURE architecture -->

**图 2-1 系统总体架构。** 实线表示数据处理方向。API 模式的文档片段和问题会发往向量服务，问题及检索资料会发往问答服务；索引与提取文本保存在本机。

建库的关键产物不是“一个向量文件”而已，而是可相互定位的三部分：FAISS 索引、Document 片段列表、索引配置签名。索引返回第 i 个向量时，系统必须能取得片段列表的第 i 项，否则检索内容和显示来源可能错位。

问答时，系统先校验配置，再调用 KnowledgeBase.search() 取回 SearchHit 列表。prepare_answer() 按字符预算组织上下文并生成 PreparedAnswer。stream_answer() 根据运行模式返回原文摘录，或调用 Prompt、聊天模型与输出解析器组成的链。app.py 消费返回的文本片段，刷新页面并保存本轮消息。

## 2.3 文件读取与文本清洗

### 2.3.1 PDF 按页提取与页码保存

read_document() 用 BytesIO 读取上传字节，再通过 PdfReader 逐页调用 extract_text()。每个非空页面构造一个 Document，页码从 1 开始记录。跳过空白页后仍保留原物理页序，例如第二页有文字、第一页为空时，来源页码仍为 2，不会变成 1。

这里的页码是 PDF 文件中的物理页序，不一定等于文档印刷页脚中的编号。封面、目录和罗马数字页码都会造成差异。后续核对引用时，应以 PDF 阅读器中的页面位置为准。

pypdf 提取的是 PDF 中已有的文本对象，不是 OCR。只有图片的扫描件无法直接产生可检索正文。双栏、公式、表格、页眉页脚也可能被抽取成不理想的阅读顺序；能够读出文字，并不等于理解了原始版式。[R7]

读取前检查文件大小，解析时检查加密和页数。不能用空密码解密的 PDF 会被拒绝；损坏文件、无可提取文本的文件会得到具体提示。批量导入中的一个坏文件通常只产生警告，不阻止其他有效文件继续处理。

### 2.3.2 TXT 编码兼容与二进制识别

TXT 若带 UTF-16 字节顺序标记，使用 UTF-16 解码；否则依次尝试 UTF-8-SIG 和 GB18030。UTF-8-SIG 可以处理 UTF-8 BOM，GB18030 为常见中文编码提供兼容。程序还统计非换行、回车和制表符的控制字符比例，减少把二进制文件误当文本导入的情况。

文件扩展名限制并不能完全保证内容合法，因此系统同时检查扩展名、文件字节和解析结果。InputFile.safe_name 只保留文件名部分并清理不可打印字符，上传文件名不会被当作任意本地写入路径。

### 2.3.3 规范化与清洗的收益及代价

clean_text() 使用 Unicode NFKC 规范化，统一兼容字符形式；把 CRLF 和 CR 统一为换行；删除空字符、BOM 和零宽空格；压缩行内空白及连续空行。清洗可以减少视觉相同但编码不同的内容差异，并降低无意义空白对分段的影响。

清洗不是无损转换。例如全角字符可能变成半角，某些依赖精确空白的代码或表格会失去格式。系统保存的 start_index 指向清洗后页面文本的位置，不是原始 PDF 字节偏移。对于源代码、法律条款或必须逐字复核的材料，需要人工查看原文件。

## 2.4 递归分段与来源元数据

### 2.4.1 为什么需要把文档分成片段

整篇文档直接生成一个向量，会把多个主题混合在一起；整篇作为 Prompt 又可能超出模型上下文限制，增加费用和噪声。分段把检索粒度缩小到局部知识，使系统有机会只选择回答所需的资料。

项目使用 RecursiveCharacterTextSplitter，依次尝试段落、换行、中文句号、感叹号、问号、分号、空格等分隔符。只有较大单元仍然超长时，才进一步切成较小单元。字符递归切分及面向中文增加标点分隔符的原则可见 LangChain 文档。[R2]

默认 chunk_size 为 600，chunk_overlap 为 100，单位均为字符，而不是 token。重叠有助于保留跨边界的事实联系，但实际重叠由分隔符与拼接逻辑决定，不保证每两个片段都恰好重复 100 个字符。

### 2.4.2 分段参数如何影响效果

片段太短，问题的条件、结论或例外可能被分开；片段太长，主题混杂、检索定位变粗，也会占用更多上下文。重叠太少容易丢失边界信息，重叠太多会增加向量数量，并使 Top-K 被重复内容占据。因此，600/100 是原型默认值，不是适用于所有材料的最优参数。

例如，“先做向量归一化，再计算内积，此时内积等于余弦相似度”应尽量保留在相邻的局部上下文中。如果分段刚好把“归一化”条件与“内积等于余弦”结论分开，模型可能得到不完整依据。合理分段的目标是保留完整知识单元，而不仅是平均分配字符数。

### 2.4.3 元数据与片段唯一标识

| 字段 | 含义 | 使用位置 |
| --- | --- | --- |
| source | 清理后的文件名 | 引用标题、文档列表 |
| file_hash | 原始文件字节的 SHA-256 | 文件去重、版本区分、统计 |
| page | PDF 物理页序；TXT 为 None | PDF 来源定位 |
| start_index | 片段在清洗后页文本中的起点 | 片段定位与 ID 构造 |
| chunk_number | 本次文件分段后的顺序号 | 预览辅助信息 |
| chunk_id | 来源哈希、页码、位置和文本组合的 SHA-256 | 检查重复片段和展示短 ID |

文件去重依据原始字节，而不是文件名。相同内容改名后仍会被跳过；同名文件内容改变则作为新文档导入。两个语义相同但字节不同的文件不会自动合并，这不是语义去重。

## 2.5 Embedding 模型与向量归一化

### 2.5.1 向量模型与问答模型的分工

Embedding 模型接收文本，输出固定维度的数值向量，用于比较问题和资料的接近程度。问答模型接收问题与参考文本，生成自然语言答案。两者是独立任务，支持聊天接口的服务未必支持向量接口，不能把聊天模型名直接填进 Embedding 模型字段。

build_embeddings() 创建 OpenAIEmbeddings 并包装为 UnitEmbeddings。问答侧的 build_chat_model() 创建 ChatOpenAI。两套配置分别指定 API Key、Base URL 和模型名，因此可以由不同服务商提供。LangChain 的对应集成提供统一的客户端对象；具体第三方接口是否兼容仍需要实际验证。[R3][R6]

向量适配设置 check_embedding_ctx_length=False，使请求发送文本字符串，避免向 OpenAI 兼容服务发送只适合特定 tokenizer 的 token ID。这个设置同时意味着项目没有依赖客户端自动分割超长输入；仍须确保字符分段后的实际 token 数不超过服务限制。

### 2.5.2 归一化内积为何等于余弦相似度

设查询向量为 q，文档向量为 d。余弦相似度等于二者内积除以各自长度的乘积；当两者分别归一化到单位长度后，直接计算内积即可得到余弦相似度。[R4]

<!-- EQUATION cosine -->

**式 2-1 余弦相似度与单位向量内积。** 非零向量先归一化，才能把内积解释为余弦相似度。

UnitEmbeddings.normalize() 把返回值转换为 float32 矩阵，检查二维形状、非空维度和有限数值，再按行计算 L2 范数并相除。分母设置不小于 1e-12，以避免除零。零向量会保持为零，不能把它当成包含有效语义的单位向量。

文档与查询都必须经过同样处理。若只归一化一侧，文档向量长度仍可能影响分数。更重要的是，建库和查询必须使用同一套向量模型与表示方式；两个不同模型即使都输出 1024 维，也不意味着向量空间可以混用。

### 2.5.3 离线模式的实现与限制

DemoEmbeddings 将英文词语与中文连续字符中的二元、三元字符片段进行哈希，累计到固定的 2048 维桶中，再由 UnitEmbeddings 归一化。其结果确定、无需联网，适合验证流程、排序和保存恢复。

它没有通过语义训练学习同义表达，存在哈希碰撞，不能作为真实语义 Embedding 的质量替代。离线回答直接展示检索到的原文，界面会明确标记未调用大模型。离线成功说明管线可运行，不说明生成模型已经连接成功。

## 2.6 FAISS 索引与相关片段检索

### 2.6.1 IndexFlatIP 的选择

项目使用 faiss.IndexFlatIP。Flat 表示保存完整向量并逐个比较，IP 表示以内积为检索分数。经过双侧归一化后，这一分数可以用于余弦相似度排序。该索引属于精确检索，不需要预训练聚类中心，也没有使用 IVF、HNSW 或 PQ 近似索引。[R4][R5]

“精确检索”只表示在给定向量空间中准确找到最高分向量，不代表找到了业务上最正确的证据。向量模型不合适、分段不完整、问题过于模糊，都可能使精确计算返回不理想内容。

### 2.6.2 Top-K 与阈值过滤

search() 首先清理问题并限制长度为 2000 字符以内；知识库为空时返回空结果。有索引时，系统调用 embed_query() 生成并归一化查询向量，检查其维度，再向 FAISS 请求 min(K, N) 条结果，最后仅保留分数不低于阈值的片段。

默认 K=4，最低相似度为 0.12。K 是返回数量上限，阈值是最低向量相关程度；设置阈值后，返回数量可能少于 K，甚至为零。相似度在此不是概率，也不是答案置信度，更不是可对外报告的回答准确率。

系统按 FAISS 返回的向量位置取出对应 Document，封装为 SearchHit。当前没有重排序、来源多样性控制或相邻片段合并。因此，重叠较多的相似片段可能同时进入 Top-K，并挤占上下文预算。

### 2.6.3 复杂度与规模估算

若有 N 个 d 维向量，单次精确比较的主要计算量随 N×d 增长；纯 float32 向量数组的存储量约为 4Nd 字节。[R5] 当前 116×1024 维向量约占 464 KiB；10000×1024 维约占 39.1 MiB。这里是数组容量估算，不是实际进程内存或磁盘压缩文件大小。

元数据、Python 对象、查询中间结果和候选索引克隆还会占用额外内存。API 网络请求和模型生成也可能主导端到端耗时。因此，不能只根据向量数组较小，就宣称系统具备高并发或毫秒级问答能力。

## 2.7 增量导入与本地持久化

### 2.7.1 增量导入的更新顺序

ingest() 先检查批量限制，收集已有 file_hash，再逐个读取新文件、分段和汇总警告。重复文件跳过，新增内容才调用 Embedding。若某个文件解析失败，其他有效文件可以继续；若没有任何可导入的新内容，则返回重复报告或抛出可读错误。

程序不会立即在活动索引上追加向量，而是构造候选索引。增量导入时克隆旧 FAISS 索引并复制文档列表；重建时创建新的空索引。新向量和新片段加入候选对象后，只有保存成功，self.store 才切换到候选对象。

**图 2-2 导入成功后的提交顺序。** 向量接口失败或保存失败时，不把未完成的候选数据切换为当前活动知识库。

这种方式体现了事务式更新的思路：先准备新状态，再提交。但它不是数据库事务，也没有实现并发锁。两个进程或会话同时写同一路径，仍可能发生后写覆盖，因此当前应按单用户使用。

### 2.7.2 NPZ 文件中保存什么

_save() 用 faiss.serialize_index() 得到内存字节，再与 JSON 元数据一起保存到 knowledge.npz。元数据包括 schema 版本、配置签名、向量维度、更新时间、FAISS 字节的 SHA-256，以及各片段文本和 metadata。读取时使用 np.load(..., allow_pickle=False)，不反序列化 Python 文档对象。

写盘先在目标目录创建临时文件，flush 和 fsync 后调用 os.replace() 替换目标文件，最后清理临时文件。通过内存字节序列化还能减少 FAISS 直接处理中文路径时的兼容问题。

原始上传文件不会额外保存，但清洗后的片段原文会写入 NPZ。索引没有加密，不能把“没有保存原始 PDF”理解为“本机没有敏感内容”。SHA-256 校验用于发现字节变化，不提供加密，也不能防止有权限修改文件的人同时重写校验值。

### 2.7.3 索引恢复与配置一致性

load() 检查 schema、配置签名和二进制校验值，反序列化索引并重建 Document 列表，再检查片段 ID、向量数量、维度、内积度量及 IndexFlatIP 类型。索引损坏或不兼容时，页面阻止直接提问并给出重建提示。

配置签名包含 Embedding 的类型、服务地址和模型名，以及分段长度、重叠长度和预处理版本。密钥、聊天模型和检索阈值不写进签名：更换这些参数不会改变文档向量本身。更换 Embedding 或分段参数则需要恢复原配置，或用完整目标文件集合重建。

离线与 API 索引分别保存在 demo 和 api 子目录。两个模式既不共享向量维度，也不混用文件。当前仅维护每个模式的一份活动索引，没有多版本索引注册表或自动备份恢复机制。

## 2.8 上下文构建与生成式问答

### 2.8.1 从检索结果组织参考资料

prepare_answer() 为每条资料添加本轮引用编号、文件名和可用页码，再拼接正文。总预算默认为 10000 字符，预算同时考虑标题和片段间分隔符；最后一个片段可能被截断，后续片段可能因预算不足而不再加入。

页面显示的 sources 使用实际放入上下文的截断文本，避免出现“页面展示了一整段，但模型只看到了前半段”的证据错觉。引用编号仅在本轮回答内有效，不是全局文档 ID。

字符预算与模型 token 预算不是同一概念。英文、中文、代码和特殊符号的字符/token 比例不同，而且系统提示词、问题和生成回答也占用窗口。当前实现属于字符级限制，若要更精确控制费用和上下文长度，需要针对实际模型增加 token 统计。

### 2.8.2 Prompt 规则与链式组合

系统提示词要求模型用中文、仅依据本轮参考资料回答、资料不足时明确说明、重要结论标注引用、资料冲突时提示冲突，并要求把资料中的指令当作待分析数据。用户消息包含明确的资料起止标记和当前问题。

核心链的实际组合形式为：

```python
chain = PROMPT | build_chat_model(settings) | StrOutputParser()
for token in chain.stream({"context": context, "question": question}):
    if token:
        yield token
```

管道符组合的含义是把上一步输出交给下一步：Prompt 构造消息，ChatOpenAI 调用模型，StrOutputParser 提取字符串。本项目没有使用自动规划、工具选择循环或复杂 Agent 状态图，固定 RAG 链已经能够覆盖当前需求。

### 2.8.3 无证据与引用可靠性

若筛选后没有来源，stream_answer() 直接返回“当前知识库中没有找到足够相关资料”的提示，不调用聊天模型。这样能减少没有依据时的额外生成，但不等于完整的可回答性识别：检索到了高相似片段，仍可能缺少问题所需的关键事实。

引用编号由模型生成，参考片段由检索管线提供。当前没有程序逐句核验“这一结论是否被这一引用支持”，也没有强制阻止模型输出不存在的编号。因此，Prompt 和来源展示只能帮助约束与复核，不能保证完全消除幻觉。

### 2.8.4 流式展示与中断处理

ChatOpenAI 使用 Chat Completions 接口，显式关闭 Responses API 路径及流式用量扩展。页面逐步消费文本，把已经收到的 pieces 拼接到占位区域。流式输出改善等待过程中的可见性，但不意味着模型总生成时间一定减少，也不保证每个 SDK 文本片段正好对应一个 tokenizer token。

发生网络中断时，页面保留已经显示的部分回答，并标记未完成。若模型没有返回任何有效文本，程序提示空回答。SDK 最多重试 2 次，不应据此承诺已开始的流可以自动续接；项目没有实现断点续写。

## 2.9 Streamlit 页面与状态管理

页面由侧边栏和三个标签页组成。侧边栏提供配置、文件选择、导入、示例加载与重建；知识问答页展示问题、回答与参考片段；我的文档页展示数量及预览；使用说明页解释模式和限制。

Streamlit 交互通常会触发脚本重新执行。st.session_state 用于在同一用户会话的 rerun 之间保留设置、知识库实例、已加载设置、消息和导入报告，这是会话状态机制的典型用途。[R8] 页面设置通过 form 一次提交，减少未完成配置被立即应用的情况。

应用检测到 Settings 与 loaded_settings 不同时，会创建 KnowledgeBase 并尝试恢复对应索引，同时清空当前对话。成功新增文档后也清空原对话，避免把旧知识库状态下的答案与新资料混在一起。仅重复导入、没有新增内容时，不需要重新生成已有文档向量。

对话记录只保存在当前会话。新会话能够恢复磁盘索引，但不会自动恢复旧聊天和页面填写的密钥。项目也没有用全局缓存保存密钥或活动文档；这减少跨会话混用风险，但共享磁盘路径仍不具备多人数据隔离。

文档预览按完整 file_hash 分组，标题显示短内容 ID。这样同名文件的不同版本会显示各自内容；仅按文件名查找第一条片段会误把所有版本都预览成第一版，这是本项目已经修复并加入回归测试的具体问题。

## 2.10 配置加载与错误反馈

Settings.from_env() 读取项目 .env，并保留已存在环境变量的优先级。LLM_* 与 EMBEDDING_* 配置独立；未填写专用密钥或地址时，可以使用 OPENAI_API_KEY 和 OPENAI_BASE_URL 作为公共后备。页面配置通过 dataclasses.replace() 生成新对象，经 validate() 后才应用。

validate() 检查模式、分段范围、重叠小于分段、Top-K、相似度、批量大小和超时。应用 API 设置时先允许保存尚未补齐密钥的配置，真正需要 Embedding 或聊天时再要求对应密钥与模型名。

地址校验拒绝常见控制台域名、完整资源路径，以及包含查询参数、锚点或登录凭据的 URL。Base URL 应是 API 前缀，不能把模型广场网页或已经包含 /embeddings 的完整接口地址直接当成前缀。校验只能排除已知错误，不能代替真实的网络连通与兼容性验证。

user_error() 将认证、限流、超时、连接失败、索引不兼容和文件错误转换为中文提示。对未知异常只记录类型和调用位置，不直接回显服务商响应、异常消息或局部变量，避免其中夹带密钥和文档内容。

模拟 SSE 逐条返回模型文本，再由实际客户端解析为流式输出。测试还检查恢复索引后，不重新为已有文档生成向量。这种验证能够发现接口拼接和请求结构错误，但无法证明外部服务的额度、网络稳定性和模型能力。

### 3.2.3 页面成功与异常路径

Streamlit AppTest 在没有手工浏览器操作的情况下驱动页面组件，可设置聊天输入、点击按钮并检查渲染结果。[R9] 项目页面测试涵盖示例导入、回答、来源、导出控件和新会话恢复。

API 页面测试分别模拟正常结束与中途 ReadError。正常路径应展示完整回答和参考片段；中断路径应保留已生成文本、显示“未完成回答”提示、保存安全的错误信息，而不是静默把半截答案当成最终答案。同名文件版本测试验证两个预览标签不同，正文也分别对应各自内容。

## 3.4 效果评价方案

现有测试主要证明功能正确性。若要在课程报告或面试中报告“检索准确”“回答可靠”或“节省时间”，应额外建立固定题集。建议从资料中准备事实题、跨片段题、同义改写题、边界题和知识库外问题，并为每题标注参考答案及相关文件页码或原文范围。

题集应保留一部分作为最终测试集，调参时只使用开发集。相关依据最好锚定原文件页码和原文范围，而不是仅保存某次分段的 chunk_id，否则分段策略变化会让标注难以比较。重叠片段应避免被重复计算成多个独立相关事实。

| 指标 | 计算或核对方式 | 使用条件 |
| --- | --- | --- |
| Hit@K | 前 K 条中至少有一条相关依据的问题比例 | 适合每题至少有一处可回答证据的情况 |
| Recall@K | 每题取回的相关证据数 / 标注相关证据总数，再求平均 | 需要较完整的相关证据标注与明确计数单位 |
| MRR | 首条相关结果排名的倒数，再对问题求平均 | 关注相关依据是否排在前面 |
| 回答支持程度 | 将重要结论逐条与参考原文核对 | 不能只看语句是否流畅 |
| 引用正确性与覆盖 | 引用是否存在、支持结论；重要结论是否有依据 | 编号存在和证据充分是两个层次 |
| 无答案处理 | 对资料不足的问题检查是否明确说明 | 同时观察错误回答和过度拒答 |
| 响应耗时 | 分别记录查询向量、检索、首段输出、完整回答时间 | 多次运行，记录模型、网络与资料规模 |
| 调用成本 | 按服务商实际用量记录导入与每问消耗 | 字符数不能精确替代实际计费用量 |

可对比“关键词检索”“当前向量检索”“调整分段后的向量检索”，也可在允许使用模型的条件下比较无参考资料与有参考资料的回答。比较前应固定题目、资料版本和评价口径。本报告给出的是后续评价设计，没有把它写成已经完成的对照实验。

## 3.5 结果解读与验证边界

目前能够支持的结论是：项目已经打通文档处理、本地索引、检索、问答接口和页面展示流程，并对常见失败路径建立了自动化保护。它可以作为完整的个人知识库原型及工程学习项目。

目前不能支持的结论包括：适用于任意 PDF；保证回答无幻觉；已经在真实服务上达到某个准确率；支持生产级多人并发；所有异常都会自动恢复；比其他系统快某个百分比。这些说法分别需要版式、模型质量、评测、压力、故障注入和对照数据。

# 第四章 关键方法与工程注意事项

## 4.1 方法与知识点对应关系

| 知识点 | 本项目中的具体运用 | 应理解的核心 |
| --- | --- | --- |
| RAG | 先查知识库，再用证据生成回答 | 外部知识更新与模型权重更新不同 |
| 文本预处理 | 编码兼容、NFKC、空白清洗 | 规范化会改变表示，应保留来源 |
| 递归分段 | 标点优先、长度限制和重叠 | 粒度、语义完整性与成本的权衡 |
| 向量表示 | 文档与问题使用同一 Embedding | 维度相同不保证语义空间相同 |
| 线性代数 | L2 归一化、内积、余弦相似度 | 归一化条件决定分数的解释 |
| 信息检索 | Top-K、阈值、相关结果排序 | 检索相关性不等于答案真实性 |
| Prompt 设计 | 资料边界、缺证据提示、引用规则 | 提示词是约束手段，不是正确性证明 |
| 内容寻址 | SHA-256 文件哈希与片段 ID | 按内容识别资料，不依赖文件名 |
| 一致性保护 | 配置签名、维度与数量检查 | 避免向量、片段和配置错配 |
| 事务式更新 | 候选索引、临时文件、原子替换 | 成功提交前保留旧状态 |
| API 集成 | 独立密钥地址、超时、流式响应 | 接口协议与模型角色都需匹配 |
| 软件测试 | 临时目录、MockTransport、AppTest | 区分算法、接口、页面与真实效果 |

这些知识点的价值在于能够解释“为什么这样实现”和“什么条件下会失败”。面试或项目讲解时，单纯列出库名不如围绕一个问题说明数据流、设计取舍和验证证据。

## 4.2 分段与检索参数的调试方法

先建立少量已知答案问题，查看原文抽取质量，再决定是否调分段。若抽取内容已经错乱，单纯增大 Top-K 通常不能恢复丢失的结构。若证据被切断，应先调整分隔符、分段长度或邻接上下文；若证据完整但排序靠后，再考虑模型、查询表述或检索策略。

| 参数 | 当前默认值 | 调大或调整时的主要影响 |
| --- | --- | --- |
| CHUNK_SIZE | 600 字符 | 保留更多上下文，但向量主题可能更混杂 |
| CHUNK_OVERLAP | 100 字符 | 减少边界丢失，但重复与调用量可能增加 |
| TOP_K | 4 | 增加资料覆盖，也可能引入无关或重复片段 |
| MIN_SIMILARITY | 0.12 | 调高可减少低分结果，但可能漏掉相关资料 |
| MAX_CONTEXT_CHARS | 10000 | 增加资料预算，同时增加输入与窗口压力 |
| EMBEDDING_BATCH_SIZE | 16 | 影响单次请求规模，需匹配服务商限制 |
| API_TIMEOUT | 60 秒 | 允许较慢请求继续等待，不解决错误地址或余额问题 |

阈值应根据实际模型和题集校准。不同 Embedding 模型的分数分布可能不同，0.12 不是通用的“相关/不相关”分界。不要把阈值设得极低来掩盖检索问题，也不要仅为得到整齐的 K 条结果而接受明显无关片段。

分段参数变化会改变片段集合，因此需要重建文档向量；仅调整 Top-K、阈值或聊天模型不需要重算已有向量。一次只改一类因素，保留题集、配置和结果记录，才能判断变化来自哪里。

## 4.3 API 配置与调用成本

Base URL、模型名和密钥是三项独立条件。地址应填写接口前缀；模型名必须是对应服务支持的模型标识；密钥必须属于该服务并有权限和额度。问答可用但导入失败时，应检查 Embedding 配置，而不是反复更换聊天模型。

建库通常会为新增片段调用向量接口；每次提问会调用一次查询向量流程，有相关资料时再调用聊天模型。恢复索引本身不需要重新生成文档向量。内容哈希去重减少重复导入费用，但重建会为目标集合重新生成向量。

即使输入只有 600 字符，仍需要核对向量服务的 token 上限与批量限制；若接口限制每批输入数较小，可以降低 EMBEDDING_BATCH_SIZE。不能把所有 400 或 404 错误都用“批量设为 1”解决，首先应看地址前缀、模型名与接口类型。

服务超时和最多两次重试可能延长总等待时间，API_TIMEOUT 不是整个问答流程的总时长上限。并发、限速、退避策略和配额监控是后续扩展时需要另行设计的能力。

## 4.4 数据安全与可信引用

API 模式会把提取的文档片段发送给向量服务，把问题发送给向量服务，并把问题及检索资料发送给问答服务。索引在本地保存，并不等于整个系统的数据处理完全离线。使用个人、组织或保密资料时，应先确认允许发送到所配置的服务。

当前密钥默认只保存在会话；若写进 .env，则属于本机明文配置，需要做好文件权限和版本控制排除。不能把真实密钥放进报告、截图、源代码或可分享压缩包。日志只记录必要调用位置的做法有助于降低泄露，但仍应检查后续新增日志是否输出敏感内容。

文档中的恶意指令可能试图覆盖问答规则。项目在系统提示词中要求将参考资料作为数据处理，但没有完整的提示词注入检测或权限控制。来源展示可以帮助人工发现问题，不能作为自动安全证明。

NPZ 使用 allow_pickle=False、校验值和元数据检查，能够减少错误反序列化与意外损坏风险。它仍不是一个面向不可信第三方索引的安全导入格式。当前设计应读取程序自己生成且来源可信的索引，不应把任意外部 NPZ 当成安全文件加载。

## 4.5 资料维护与运行边界

增量导入是追加新内容，重建是用完整的目标资料集合替换现有库。同名新版不会自动删除旧版；需要去掉旧版时，应准备全部要保留的资料再重建。如果批量重建时有文件无效，它可能被跳过，成功入库的有效集合仍会替换原库，因此必须核对导入报告。

导入失败保护主要覆盖单次活动更新与写盘失败，不涵盖所有突然断电、磁盘损坏、多个进程同时写入或人为删除。重要资料应保留原文件与独立备份。Atomic replace 有助于避免半写文件，但不是完整的备份策略。

页面历史记录与磁盘知识库生命周期不同。刷新或新会话后，资料索引可以恢复，聊天记录和页面密钥可能丢失。向量模型不变时无需因为聊天密钥丢失而重新上传全部文件，只要补齐配置即可继续检索。

默认本机监听减少意外暴露，但这不是用户认证。如果要部署到服务器，不能仅将地址改为 0.0.0.0 就声称支持多人使用；还需要身份认证、独立存储路径、并发写保护、网络访问控制和日志管理。

## 4.6 项目特色与可陈述的工程成果

本项目的特点是以较小的代码规模实现了可追溯的完整 RAG 流程，明确区分离线与 API 行为，并把模型配置一致性、失败保护和页面异常路径纳入工程实现。它的价值主要是完整性、可理解性和可复现性，不宜包装成新的基础检索算法或模型训练成果。

与只演示“上传后能回答”的最小脚本相比，本项目额外处理了文件编码、真实页码、哈希去重、配置错配、持久化、流式中断和同名版本预览等问题。每项特色都应对应代码位置和测试证据，而不是只写抽象的“高效、智能、可靠”。

可以陈述“完成可运行的文档知识库问答原型，支持 PDF/TXT 导入、向量检索、流式回答和参考原文展示，具备本地恢复与自动化验证”。若要进一步陈述节省检索时间、提高正确率等效果，需要先完成本报告第三章所述的质量与耗时评测。

## B.3 常见现象与定位顺序

| 现象 | 优先检查 | 处理思路 |

# 附录 C 项目理解与答辩问题

## C.1 RAG 与微调有什么区别

本项目的文档知识保存在外部片段与向量索引中，提问时检索后临时提供给模型。微调则通过训练更新模型参数。RAG 更便于增补资料和展示来源，但其效果依赖解析、分段、检索与生成各环节。本项目没有微调，也没有训练自己的向量模型。

## C.2 为什么 FAISS 不能直接回答问题

FAISS 接收向量并返回相似向量的位置与分数，不理解页面如何展示引用，也不生成自然语言。原文来自 Document 列表，回答来自聊天模型；把三者连接起来才构成完整问答系统。

## C.3 为什么相同维度仍可能不能混用

维度只说明向量有多少个分量，不说明分量的语义或训练得到的空间结构。不同模型的坐标空间可能完全不同。项目通过地址、模型名和预处理配置签名减少混用，并通过实际维度检查发现返回形状变化。

## C.4 怎么减少幻觉与误导

先提高原文和检索质量，避免无证据时仍然生成；再设置资料边界、缺证据说明与引用要求；最后展示实际输入模型的原文，允许用户核对。项目已经实现这些基础措施，但没有证明完全防止幻觉，后续应增加题集评测和逐条引用支持检查。

## C.5 为什么不一开始就使用复杂 Agent

当前需求的数据流明确：读文件、检索、组织资料、生成回答。固定管线更容易观察和测试。只有后续出现需要动态选择工具、跨步骤规划或多数据源操作的明确需求，才有充分理由增加 Agent 编排。

## C.6 怎样描述自己的实际工作

应先讲用户问题，再讲实现动作与验证证据，例如“完成文档读取与分段，保留来源；对接独立的向量和聊天接口；使用归一化向量与 FAISS 检索；通过页面展示回答和原文；补充持久化与异常回归测试”。结果描述限于已经验证的原型能力，不把计划功能、接口模拟或估算容量写成真实业务成绩。
