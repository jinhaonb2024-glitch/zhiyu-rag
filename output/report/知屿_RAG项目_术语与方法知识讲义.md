# 读懂 RAG 项目报告：专业术语与方法知识讲义

适用对象：已能运行项目，但对人工智能、向量检索和软件工程术语还不熟悉的读者。

这份讲义不要求你先学完机器学习或线性代数。先把整体过程想清楚，遇到生词再查。所有类比都服务于理解；实际边界以原报告和项目实现为准。

## 怎么使用这份讲义

**第一遍，建立画面。** 先读下一节“把系统想成带检索员的资料室”，再读标有“先读”的词条。你暂时不用记住每个工具名和函数名。

**第二遍，带着报告查词。** 词条按它们在原报告文字源稿中最早出现的位置排列；中文、英文与代码别名合并讲解。同一概念只解释一次。每条给出章节及对应 PDF 的首次文字页码；封面与摘要计入，自动目录不计入。

**第三遍，动手算一次。** 阅读最后的向量计算、分段、检索筛选和评价指标例题，再用自测题检查理解。你能用自己的话解释“输入是什么、做了什么、为什么这样做、哪里可能出错”，就比只记缩写更接近掌握。

“先读”是理解主流程的核心词；“查阅”是看到时再读的实现基础；“进阶”是运行维护或后续扩展知识；“补充”是在原报告之外增加的少量必要基础。首次位置的映射针对上一份 29 页报告，更新报告后页码可能改变。

## 把系统想成带检索员的资料室

你是来提问的人，原始 PDF/TXT 是资料；清洗与分段把资料做成小卡片；metadata 是每张卡片的出处标签；Embedding 给卡片和问题生成可比较的数值表示；FAISS 帮忙挑出较接近的卡片；Prompt 把问题、卡片和作答规则交给问答模型；Streamlit 展示回答与出处。

**建库是一段准备工作：** 原文件 → 读出文字 → 整理文字 → 切成片段并加出处 → 编码为向量 → 建索引并保存。

**提问是另一段工作：** 当前问题 → 用同模型编码 → 取相近片段 → 按阈值和预算筛选 → 连同问题交给问答模型 → 显示回答与依据。

这个类比有三处需要守住边界：向量不是带可读主题标签的真实书卡；FAISS 选的是数值相关候选，不会核实答案；问答模型组织语言时仍可能添出原文没有的内容。因此，最后的人工核对不可省略。

# 封面与摘要中首次遇到的术语

## 001 RAG：检索增强生成

阅读级别：先读。原报告首次：封面；PDF 第 1 页。

**怎么理解：** 让程序先从资料中找依据，再把依据交给模型组织答案。可以把它理解成“开卷回答”：先翻书，再作答。RAG 的英文全称是 Retrieval-Augmented Generation。

**放进本项目：** 你问“FAISS 怎样实现余弦检索”，程序先找知识库中的相关段落，再请问答模型解释这些段落。

**容易误解：** 上传文件主要改变外部知识库，不会因此训练或改写大模型权重。检索和生成都可能出错，RAG 不保证答案完全正确。

## 002 知识库

阅读级别：先读。原报告首次：封面；PDF 第 1 页。

**怎么理解：** 在本项目中，知识库是整理好、能够被程序检索的一组资料及其配套数据。它不像人的大脑，而像带检索工具的资料柜。

**放进本项目：** 柜子里既有片段正文和来源信息，也有为检索准备的向量及索引。

**容易误解：** 知识库不是大模型本身，也不等于保存着原始 PDF 的文件夹。本项目保存提取后的片段，不另外存上传原件。

## 003 Python

阅读级别：查阅。原报告首次：封面；PDF 第 1 页。

**怎么理解：** 一种编程语言。你写下处理步骤，Python 解释器按这些步骤运行程序；.py 是常见的 Python 源代码文件扩展名。

**放进本项目：** app.py 负责页面交互，rag/ 下的代码负责读文件、检索和调用模型。

**容易误解：** Python 是语言，LangChain 等是安装在这门语言环境中的工具包；二者不是同一层级的东西。

## 004 LangChain

阅读级别：先读。原报告首次：封面；PDF 第 1 页。

**怎么理解：** 帮助开发者连接文本、提示词、模型和其他工具的软件框架。可以理解成一套已经做好的连接件，减少重复拼接工作。

**放进本项目：** 项目借它表示文档、切分文本、适配模型接口，并把提示词、聊天模型和输出解析器串起来。

**容易误解：** 框架不会自动替你保证资料质量，也不是某一个大语言模型。本项目只用了其中的一部分能力。

## 005 FAISS

阅读级别：先读。原报告首次：封面；PDF 第 1 页。

**怎么理解：** 用于比较和检索大量数值向量的软件库。可以把它看作“向量资料柜的查找器”。它的英文名称是 Facebook AI Similarity Search。[S1]

**放进本项目：** 项目把片段向量放入 FAISS，查询时取回较相近向量的位置和分数，再按位置找到原文。

**容易误解：** FAISS 不负责生成回答，也不会自动保存完整的文件名、页码和原文关系；这些由项目代码维护。

## 006 Streamlit

阅读级别：先读。原报告首次：封面；PDF 第 1 页。

**怎么理解：** 用 Python 快速制作网页交互界面的工具。开发者主要写 Python，就能得到输入框、上传框、按钮和聊天区域。

**放进本项目：** 侧边栏配置、文档上传、聊天回答、来源展开区都由它显示。

**容易误解：** 它是界面工具，不是向量检索算法，也不是大模型。界面能打开，不代表模型服务已经连通。

## 007 API 与 OpenAI 兼容 API

阅读级别：先读。原报告首次：封面；PDF 第 1 页。

**怎么理解：** API 是 Application Programming Interface，即程序调用另一个程序的约定。这里可理解成服务窗口规定的“请求格式、地址和返回格式”。OpenAI 兼容表示采用相近的接口约定。

**放进本项目：** 项目用同一类客户端，按各自地址、密钥和模型名调用问答服务与向量服务。

**容易误解：** “兼容”不等于所有功能都完全一样，也不等于服务由 OpenAI 提供。聊天兼容并不自动说明向量接口兼容。

## 008 PDF 与 TXT

阅读级别：查阅。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** PDF 侧重保留页面外观；TXT 主要保存纯文本。一个 PDF 看起来有文字，内部也可能只是文字的照片。

**放进本项目：** 系统对 PDF 按页提取已有文本；对 TXT 按编码规则把字节还原成文字。

**容易误解：** 扫描 PDF 通常需要先做 OCR。把图片文件改成 .txt 或 .pdf 扩展名，不会让它自动变成可提取文本。

## 009 文本清洗、规范化与预处理

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 把原始文字整理成后续步骤更容易使用的形式。清洗处理多余空白和特殊字符；规范化让某些不同写法变得一致；预处理是这类准备工作的统称。

**放进本项目：** 把多种换行统一、删除零宽空格、压缩多余空白，再进行分段。

**容易误解：** 清洗可能改变代码缩进或表格空白，并非无损复制。抽取顺序已经错乱时，清洗也未必能恢复原版式。

## 010 递归分段、chunk 与 overlap

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** chunk 是一个文本片段。递归分段会先按较大的边界切，如段落；仍太长时再尝试换行、句号等更小边界。overlap 是相邻片段保留的重复部分。[S2]

**放进本项目：** 项目默认片段上限 600 字符，重叠目标 100 字符，尽量兼顾局部完整性和检索粒度。

**容易误解：** 600/100 是字符数，不是 token 数，也不是通用最优值；按实际分隔符拼接后，重叠未必恰好为 100。

## 011 来源信息与 metadata（元数据）

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 正文说明“讲了什么”；元数据说明“这段话从哪里来、是什么”。类似书里的内容与借书卡上的书名、页码、编号的区别。

**放进本项目：** 片段旁边记录文件名 source、页码 page、文件哈希 file_hash 和片段 ID 等。

**容易误解：** 元数据并不天然正确。向量与元数据一旦对应错位，就可能出现回答看似有引用、实际指向另一段原文的问题。

## 012 Embedding（嵌入、向量化）

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 用一个固定的转换方法，把文本变成一串数值。“语义”就是文字表达的意思；经过训练的语义 Embedding 试图让意思相关的文本具有更接近的数值表示。

**放进本项目：** 文档片段和用户问题都交给同一个向量模型编码，然后比较结果。

**容易误解：** 它通常不会生成聊天答案。把文字变成向量也不是压缩包，不能保证从向量完整还原原文。

## 013 向量、维度与向量空间

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 向量是一串有固定顺序的数字；维度是这串数字有多少个。向量空间可以先理解成大家共用的坐标规则，只有规则一致，位置才可比较。

**放进本项目：** 1024 维表示每段文本对应 1024 个数；查询也必须使用相匹配的表示方式。

**容易误解：** 维度不是文档数，也不是准确率。实际模型的一维一般不对应一个可以直接命名的“主题”，不同模型同为 1024 维也不能随意混用。

## 014 索引与建库

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 索引是帮助检索的数据结构；建库是把原资料加工成可检索状态的过程。类似先整理书卡，之后才方便查找。

**放进本项目：** 读文件、清洗、分段、生成向量并保存索引，合起来构成建库。项目的 Flat 索引仍会逐个比较向量。

**容易误解：** “有索引”不一定意味着采用很复杂的加速算法，也不意味着语义检索一定准确。

## 015 检索、关键词检索与语义检索

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 检索是从已有资料中找候选内容。关键词检索重视字面词语匹配；语义检索利用表示模型寻找意思接近的内容。

**放进本项目：** 问题写“怎样让回答有出处”，资料写“提供引用与原文”，语义模型可能把二者联系起来。

**容易误解：** 意思相近不等于能够回答问题。专业编号、数字或罕见词有时更适合字面匹配；当前系统没有实现关键词与向量的混合检索。

## 016 上下文、上下文窗口与预算

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 上下文是模型本次作答时收到的内容，包括指令、问题与参考资料。上下文窗口描述模型可容纳的范围，具体输入与输出限制要看模型规则；预算限制本次放多少资料。

**放进本项目：** 项目为检索片段加上来源标题，最多使用配置允许的字符数；最后一段可能被截断。

**容易误解：** 这不是模型自动记住了整个知识库。界面显示历史记录，也不表示历史会送进下一次调用；字符预算也不等于模型 token 上限。

## 017 Prompt、系统消息与用户消息

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** Prompt 是本次给模型的输入与要求。系统消息描述总体规则；用户消息放当前任务。在项目里，二者合起来告诉模型“按什么规则，回答哪个问题”。

**放进本项目：** 系统规则要求基于资料回答、缺证据时说明；用户消息提供带边界标记的参考资料和问题。

**容易误解：** 提示词是行为约束，不是正确性证明。资料里写着“忽略上面规则”，也不应被当成开发者授权的指令。

## 018 Chat Completions、问答模型与 LLM

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 模型可理解成通过学习形成的输入输出转换系统。LLM 是 Large Language Model，即大语言模型；问答模型据输入生成文字，Chat Completions 是组织聊天请求和响应的一种 API 形式。

**放进本项目：** 项目把参考片段和问题交给 ChatOpenAI 适配的聊天服务，接收回答文本。

**容易误解：** 模型“表达得像真的”并不能证明内容真实。它与 Embedding 的任务不同，不能简单互换模型名。

## 019 流式输出与文本片段 pieces

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 不等整段回答结束，就持续把已经生成的部分发送并显示出来，类似边听直播边看到字幕。

**放进本项目：** 页面把每次收到的字符串追加到已经显示的回答后面。

**容易误解：** 一块网络文本不一定对应一个 token。流式改善等待时的可见性，不保证总耗时更短；中断后已显示文字仍可能是不完整答案。

## 020 模块化、接口与适配层

阅读级别：查阅。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 把程序按职责分成若干部分，并约定各部分接收什么、返回什么。适配层负责把不同外部服务的差异整理成项目能统一使用的形式。

**放进本项目：** documents.py 处理文档，providers.py 接模型，qa.py 组织问答，app.py 展示页面。

**容易误解：** 模块多不等于结构好。关键在职责是否清楚，修改一个模块时是否无需改动所有其他模块。

## 021 文件哈希、SHA-256、去重与内容寻址

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 哈希把任意长的数据算成固定长度的摘要。SHA-256 是一种具体方法。按摘要识别内容叫内容寻址；比较摘要可用于识别重复文件。

**放进本项目：** 同一文件改名仍会得到相同内容哈希，因此跳过；同名文件改了内容，通常会得到不同摘要，因此作为新版本加入。

**容易误解：** 它不是加密，也不是语义理解。两份意思一样但字节不同的文件不会因此自动去重；哈希碰撞在理论上可能存在。

## 022 索引配置签名与一致性校验

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 把决定向量含义和片段划分的重要设置记录下来，恢复索引时比较是否一致。这里的“签名”是配置标识，不是密码学数字签名。

**放进本项目：** 比较向量服务地址、模型、分段参数和预处理版本，避免用新编码规则查询旧向量。

**容易误解：** 换问答密钥或聊天模型通常不要求重算文档向量；换 Embedding 模型或分段规则则往往需要重建。

## 023 候选索引、克隆与活动状态

阅读级别：查阅。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 先在一份待提交的新状态中完成修改，验证保存成功后再把它设为正式状态。克隆是复制旧索引，避免直接改坏正在使用的那份。

**放进本项目：** 增量导入先克隆旧索引、追加新向量，保存成功后才切换 self.store。

**容易误解：** 这主要保护一次更新过程。多个进程同时更新同一文件，仍可能覆盖彼此结果。

## 024 临时文件

阅读级别：查阅。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 正式文件写好前，用来暂存结果的过渡文件。就像先写草稿，确认完成后再替换正式版。

**放进本项目：** 索引先写到目标目录内的临时文件，写入成功后才替换 knowledge.npz。

**容易误解：** 临时文件本身不等于备份。提交后旧版本不一定还在；程序退出、异常或清理时也要处理遗留文件。

阅读级别：查阅。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 在操作系统提供的条件下，替换文件名这一动作作为一次完成的操作，使读者看到旧文件或新文件，减少看到半写文件的机会。[S3]

**放进本项目：** 临时文件写好后，用 os.replace 替换正式索引，再切换内存中的知识库对象。

**容易误解：** 这不等于整个流程永远不会失败，也不等于突然断电仍有完整事务保证。不能代替备份、并发控制和恢复设计。

## 026 离线模式、词面哈希与 n-gram

阅读级别：查阅。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 本项目的离线向量靠表面词语和连续字符计数，不使用训练出的语义表示。n-gram 是连续 n 个单位组成的小片段，如“向量检索”的二元片段有“向量”“量检”“检索”。

**放进本项目：** 英文词与中文二、三字符片段被哈希进 2048 个位置，累计后再归一化；回答直接摘录原文。

**容易误解：** 重复出现的表面文字可能更容易匹配，同义改写却未必匹配。不同词可能落到同一位置，这叫哈希碰撞。离线成功不证明真实模型已连接。

## 027 确定性与可复现性

阅读级别：查阅。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 确定性指同样输入与条件得到同样结果；可复现性强调别人或另一次运行能按记录条件重现结果。前者偏算法性质，后者偏完整验证过程。

**放进本项目：** 离线哈希向量在相同实现下可重复得到相同表示；记录资料、版本与设置，方便复现实验。

**容易误解：** 外部模型调用还受模型更新、服务实现和生成设置影响。只记录一条 Prompt，未必足以重现整套结果。

**放进本项目：** 测试导入重复文件不增加片段，写盘失败时保留旧库，流式中断时显示未完成提示。

**容易误解：** 38 passed 表示 38 个已写断言的测试通过，不表示 38 道真实问答都答对，也不表示没有遗漏情况。

**怎么理解：** 依赖是项目需要安装的其他软件包。版本范围允许一定变化；锁文件记录某次环境的具体版本。pip check 检查已安装包声明的依赖关系是否冲突。

阅读级别：查阅。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 快照是某一时刻状态的记录；备份是用于恢复的独立副本；版本管理帮助区分不同时间或修改状态。

**放进本项目：** 报告里的“当前索引快照”是编制时读取到的状态，不表示系统具备自动历史备份。

## 032 HTTP、客户端、服务端与请求/响应

阅读级别：查阅。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** HTTP 是网络上交换请求和响应的一套协议。客户端发起请求，服务端接收并返回结果；请求常带地址、请求头和内容，响应常带状态码和内容。[S5]

**放进本项目：** 项目的客户端把文本和模型名发给向量服务；服务端返回数值数组。浏览器也是一种客户端。

**容易误解：** 收到响应并不一定代表成功，返回的也可能是错误 JSON 或网页。要检查状态码与内容结构。

## 033 响应时延、首段输出与总耗时

阅读级别：查阅。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 响应时延是从发起操作到得到某种结果的等待时间。首段输出时间和完整回答时间是两个不同测量点。

**放进本项目：** 一次提问还可分为查询向量耗时、FAISS 检索耗时、等待聊天首段和完整生成耗时。

**容易误解：** 聊天更快开始显示，不意味着更快结束。比较应固定资料、模型、网络条件并多次记录，不能只挑最好的一次。

## 034 余弦相似度

阅读级别：先读。原报告首次：摘要；PDF 第 2 页。

**怎么理解：** 比较两个非零向量方向接近程度的数值：内积除以两者长度的乘积。方向相同为 1，垂直为 0，相反为 -1。

**放进本项目：** 文档和查询都归一化以后，内积等于余弦相似度，因此可以用 IndexFlatIP 实现这个排序。[S1]

**容易误解：** 0.8 不表示答案有 80% 正确率。不同模型的分数分布不同，需要用具体资料和题目判断阈值。

## 035 幻觉、可回答性与证据支持

**放进本项目：** 本项目调用已经存在的模型，把资料建成外部索引，没有训练自己的模型。

**怎么理解：** 解析器负责把一种形式的数据整理成下一步容易处理的形式。StrOutputParser 在这条问答链中提取文字字符串。

**放进本项目：** 模型返回消息或消息片段后，解析器把文本交给页面追加显示。

**容易误解：** 这里的“解析”没有自动核对答案真假，也没有自动验证每个引用编号。

## 054 API Key、Base URL 与模型名

阅读级别：先读。原报告首次：1.4 技术选型与职责分配；PDF 第 5 页。

**怎么理解：** API Key 用于验证调用身份；Base URL 指向服务接口前缀；模型名指定这次调用哪个模型。可类比通行证、服务地址和要办理的业务编号。

**放进本项目：** Embedding 与问答分别配置这三项。https://api.siliconflow.cn/v1 是原报告中的向量接口前缀示例。

**容易误解：** 控制台网页不是 API 前缀；不要把完整 /embeddings 路径重复填入前缀；密钥必须属于对应服务且有权限和额度。

## 055 NumPy、数组、矩阵与 batch

阅读级别：查阅。原报告首次：1.4 技术选型与职责分配；PDF 第 5 页。

**怎么理解：** NumPy 是数值计算库。向量可看成一行数；矩阵可看成很多行数排成的表；batch 是一次一起处理的一组输入。

**放进本项目：** 16 个 1024 维向量可组成 16 行、1024 列的矩阵，并按行统一计算长度。

**容易误解：** 批量大小是一次请求的输入数量，与片段的字符长度不同。减小批量不能解决错误地址或错误模型名。

## 056 L2 范数、单位向量与归一化

阅读级别：先读。原报告首次：1.4 技术选型与职责分配；PDF 第 5 页。

**怎么理解：** L2 范数是向量的长度：各分量平方求和，再开平方。向量除以自己的长度，得到长度为 1 的单位向量；这里叫 L2 归一化。

**放进本项目：** 向量 [3,4] 的长度是 5，归一化后为 [0.6,0.8]。项目对文档和查询都这样处理。

**容易误解：** 归一化主要统一长度，不是统一维度，也不是把数值都变成概率。零向量长度为 0，不能直接这样相除。

## 057 内积、点积与 IP

阅读级别：先读。原报告首次：1.4 技术选型与职责分配；PDF 第 5 页。

**怎么理解：** 两个同维向量对应位置相乘，再把乘积相加，叫点积或内积。IP 是 Inner Product 的缩写。

**放进本项目：** [1,2] 与 [3,4] 的内积是 1×3+2×4=11。FAISS 的 IP 索引按这一类分数找结果。

**容易误解：** 11 不是概率。未归一化时，向量长度也可能影响内积分数，不能直接把任何内积都解释为余弦相似度。

## 058 pytest

阅读级别：查阅。原报告首次：1.4 技术选型与职责分配；PDF 第 5 页。

**怎么理解：** 组织和运行 Python 自动化测试的工具。测试函数用断言表达“这个结果应该成立”。

**放进本项目：** 运行 pytest -q，会收集测试、执行并汇总通过或失败数量。

**容易误解：** 测试工具本身不会知道业务真相，开发者必须写有意义的输入和预期结果。

## 059 httpx、Mock 与 MockTransport

阅读级别：查阅。原报告首次：1.4 技术选型与职责分配；PDF 第 5 页。

**怎么理解：** httpx 是 Python HTTP 客户端。Mock 是为了测试而提供的可控替代；MockTransport 能在不调用真实网络服务的情况下提供 HTTP 响应。

**放进本项目：** 测试仍使用真实模型客户端解析模拟向量 JSON 和聊天 SSE，验证请求与解析路径。

**容易误解：** 模拟响应由测试者安排，只能验证对应行为，不能证明真实服务在线、有余额或模型回答正确。

# 第二章 系统设计与实现中首次遇到的术语

## 060 架构与数据流

阅读级别：查阅。原报告首次：2.1 总体架构与数据流；PDF 第 6 页。

**怎么理解：** 架构说明系统由哪些部分组成、各部分怎样协作；数据流说明信息按什么顺序经过这些部分，并怎样改变形式。可以分别理解为“分工图”和“流转路线”。

**放进本项目：** 模块分工是架构；文件字节变文字、文字变片段、片段变向量、检索结果进入模型，是数据流。

**容易误解：** 画了方框和箭头并不表示实现完成。每个箭头都应能对应实际输入输出和调用关系。

## 061 项目里的几种“数据包”

阅读级别：查阅。原报告首次：2.1 总体架构与数据流；PDF 第 6 页。

**怎么理解：** 这些是项目为不同阶段命名的数据结构，不是五种算法。InputFile 装上传文件；VectorIndex 装索引及片段；SearchHit 装命中片段与分数。

**放进本项目：** PreparedAnswer 装当前问题、实际来源和上下文；ImportReport 装新增、重复和警告，用于展示结果。

**容易误解：** 看到陌生类名时，先问“里面装什么、谁创建、交给谁”，比背英语名字更有用。函数名后面的括号通常表示调用动作。

## 062 单元测试、集成测试与页面测试

阅读级别：查阅。原报告首次：2.2 目录结构与模块接口；PDF 第 7 页。

**怎么理解：** 单元测试检查相对独立的小功能；集成测试检查多个组件如何协作；页面测试检查交互与显示路径。三者是关注范围的区别。

**放进本项目：** 清洗和分段是局部功能；模型客户端解析 HTTP 是接口集成；点击导入后能看到来源是页面行为。

**容易误解：** 某层通过不能替代其他层，更不能替代真实模型的质量评测。边界划分可因项目结构而不同。

## 063 dataclass、冻结配置与 replace

阅读级别：查阅。原报告首次：2.2 目录结构与模块接口；PDF 第 7 页。

**怎么理解：** dataclass 是 Python 为“主要用于装数据的类”自动生成一些常用方法的工具。frozen 配置阻止常规字段赋值；replace 用旧对象加新值创建新对象。[S6]

**放进本项目：** Settings 打包模型和检索配置。页面提交新设置后，创建新 Settings 并比较是否变化。

**容易误解：** 冻结不是加密，也不保证对象内部所有可变内容都递归不可改；它主要帮助减少意外原地修改。

## 064 repr=False

阅读级别：进阶。原报告首次：2.2 目录结构与模块接口；PDF 第 7 页。

**怎么理解：** repr 是对象的常用文字表示。某字段设置 repr=False，表示普通打印对象时不把这一字段列出来。

**放进本项目：** 密钥字段这样设置，可减少调试时直接打印 Settings 导致的泄露。

**容易误解：** 字段仍存在于内存，程序仍能读取。把密钥单独打印、写进日志或保存文件，依然会泄露。

## 065 加密与校验值的区别

阅读级别：查阅。原报告首次：2.2 目录结构与模块接口；PDF 第 7 页。

**怎么理解：** 加密使没有相应密钥的人难以读懂内容；校验值主要帮助发现数据变化。二者解决的问题不同。

**放进本项目：** NPZ 中记录 FAISS 字节的 SHA-256 用来核对是否变化，但原文并未因此加密。

**容易误解：** 有写权限的人可能同时修改内容与校验值。校验一致不能单独证明来自可信作者。

## 066 字节、BytesIO 与二进制

阅读级别：查阅。原报告首次：2.3.1 PDF 按页提取与页码保存；PDF 第 8 页。

**怎么理解：** 字节是文件和内存的一种基本计量单位，1 字节通常为 8 位。二进制数据是底层字节；BytesIO 把内存中的字节包装得像可读文件。

**放进本项目：** 上传框先收到字节，PDF 解析器从 BytesIO 中读取；TXT 则需按字符编码解码。

**容易误解：** 字节数不是字符数。不同编码下，一个中文字可能占多个字节；20 MB 限的是文件字节大小。

## 067 字符编码、UTF-8、UTF-16、GB18030 与 BOM

阅读级别：查阅。原报告首次：2.3.2 TXT 编码兼容与二进制识别；PDF 第 8 页。

**怎么理解：** 编码规定文字怎样存成字节；解码是按规则把字节还原为文字。UTF-8、UTF-16、GB18030 是不同规则。BOM 是文件开头可能出现的字节标记。

**放进本项目：** 项目识别 UTF-16 BOM；否则尝试 UTF-8-SIG 和 GB18030，兼容常见中文文本。

**容易误解：** 用错规则可能乱码或报错。UTF-8-SIG 表示按 UTF-8 处理并兼容开头的签名标记，不是一种“更聪明的语义编码”。

## 068 Unicode、NFKC、CRLF 与零宽字符

阅读级别：查阅。原报告首次：2.3.3 规范化与清洗的收益及代价；PDF 第 8 页。

**怎么理解：** Unicode 为文字字符规定统一标识；NFKC 是兼容规范化，例如把某些全角形式统一为对应形式。CRLF、CR、LF 是不同换行表示；零宽字符可能存在却看不见。[S7]

**放进本项目：** 把“Ａ”整理成“A”、统一换行、清理 BOM、NUL 和部分零宽空格，减少不必要差异。

**容易误解：** 不是所有看起来相似的字符都能或应当合并。规范化可能改变原表示，不能据此承诺逐字无损。

## 069 start_index、偏移量与片段 ID

阅读级别：查阅。原报告首次：2.3.3 规范化与清洗的收益及代价；PDF 第 8 页。

**怎么理解：** 偏移量表示从一段数据开头数到某处的位置。start_index 是片段在清洗后页文本中的起点；chunk_number 是顺序号；chunk_id 是较稳定的标识。

**放进本项目：** 文件哈希、页码、起点和片段文字参与生成 chunk_id，用于检查片段与显示短 ID。

**容易误解：** start_index 不是 PDF 原始字节地址；顺序号也不是全局唯一 ID。改清洗或分段方法，片段 ID 可能变化。

## 070 token 与 tokenizer

阅读级别：先读。原报告首次：2.4.1 为什么需要把文档分成片段；PDF 第 9 页。

**怎么理解：** token 是模型处理文本时的一种切分单位；tokenizer 是执行切分并映射编号的工具。一个 token 可能是词、词的一部分、字符或其他组合。

**放进本项目：** 片段按字符限制为 600，但发送给具体模型后，实际 token 数还取决于该模型的 tokenizer。

**容易误解：** 不能通用地说“一个 token 等于一个字”。不同语言、文本和模型规则会改变比例；输出流的一块文本也未必恰为一个 token。

## 071 Top-K

阅读级别：先读。原报告首次：2.4.2 分段参数如何影响效果；PDF 第 6 页。

**怎么理解：** 按分数排序后最多取前 K 条。Top 是排名靠前；K 是开发者设置的数量。

**放进本项目：** K=4 表示最多取 4 个候选片段，资料不足或阈值过滤后可能少于 4。

**容易误解：** K 不是分数，也不是固定答案长度。增大 K 可能补充证据，也可能加入重复或无关资料。

## 072 URL、域名、路径、query 与 fragment

阅读级别：查阅。原报告首次：2.5.1 向量模型与问答模型的分工；PDF 第 10 页。

**怎么理解：** URL 是资源地址。域名定位主机，路径定位服务资源，query 是问号后的参数，fragment 是 # 后的片段定位。

**放进本项目：** https://example.test/v1 的主机是 example.test，路径是 /v1；/embeddings 是具体资源路径的例子。

**容易误解：** Base URL 应是客户端所需前缀。控制台页面、重复资源路径或带敏感参数的地址，可能导致错误或泄露。

## 073 布尔配置与 check_embedding_ctx_length=False

阅读级别：查阅。原报告首次：2.5.1 向量模型与问答模型的分工；PDF 第 10 页。

**怎么理解：** 布尔值只有 True（真）和 False（假），经常表示是否启用某行为。这个配置关闭向量客户端的特定输入长度检查与处理路径。

**放进本项目：** 当前项目让接口直接收到文本字符串，避免发送某些兼容服务不接受的特定 tokenizer token ID。

**容易误解：** 关闭检查不等于模型接受无限输入，也不等于客户端会替你正确切开超长文本；仍需保证实际输入符合服务限制。

## 074 float32、有限数值、NaN 与 Infinity

阅读级别：查阅。原报告首次：2.5.2 归一化内积为何等于余弦相似度；PDF 第 10 页。

**怎么理解：** float32 是每个数用 32 位表示的浮点数类型，通常占 4 字节。有限数值排除 NaN（不是有效数值）及正负 Infinity（无穷大）。

**放进本项目：** 程序把向量转换成 float32 并检查数值；用不小于 1e-12 的分母避免直接除以 0。

**容易误解：** 浮点计算有舍入误差。1e-12 是极小保护值，不是检索阈值；零向量保留为零，也不因此具有有效语义。

## 075 IndexFlatIP、精确检索与近似检索

阅读级别：查阅。原报告首次：2.6.1 IndexFlatIP 的选择；PDF 第 11 页。

**怎么理解：** IndexFlatIP 保存完整向量并逐个计算内积分数。精确指在给定数值表示和度量下找到最高分结果；近似检索用一定取舍换速度或存储节约。

**放进本项目：** 项目采用 Flat。IVF 常借助分组筛选候选，HNSW 借助图搜索，PQ 压缩向量表示；这些是报告提到但当前未采用的方向。

**容易误解：** “精确”约束的是向量计算，不是语义与答案正确性。换近似索引前要测速度、召回和数据规模。

## 076 阈值与 MIN_SIMILARITY

阅读级别：先读。原报告首次：2.6.2 Top-K 与阈值过滤；PDF 第 6 页。

**怎么理解：** 阈值是用于保留或排除的分界值；相似度阈值用于过滤低分片段。

**放进本项目：** 相似度分别为 0.81、0.62、0.18、0.05，若最低分设 0.20，只保留前两个。

**容易误解：** 项目默认 0.12 不是各模型通用的“相关”标准。阈值过高可能漏资料，过低可能把无关资料送给模型。

## 077 复杂度、N×d 与 4Nd 字节

阅读级别：进阶。原报告首次：2.6.3 复杂度与规模估算；PDF 第 11 页。

**怎么理解：** 复杂度描述工作量怎样随输入规模增长。N 表示向量条数，d 表示维度；逐一比较的主要计算量随 N×d 增长。

**放进本项目：** float32 每个分量 4 字节，116 条 1024 维的纯向量约占 116×1024×4 字节，即 464 KiB。

**容易误解：** 这是主要数组的估算，不包括原文、Python 对象、临时副本等，也不是实际内存测量，更不能推导 API 总耗时。

## 078 并发、进程、并发锁与覆盖写

阅读级别：进阶。原报告首次：2.6.3 复杂度与规模估算；PDF 第 11 页。

**怎么理解：** 并发是多个任务的执行时间相互重叠。进程是操作系统运行程序的一种单位。锁可以规定共享资源同一时刻由谁修改。

**放进本项目：** 两个会话都从旧库开始，各写各的新库，后写者可能把前者刚加入的资料覆盖掉。

**容易误解：** 单次 os.replace 不会自动合并两个写者。当前项目没有并发写锁，不应据此宣称支持生产级多人写入。

## 079 flush、fsync、内存与磁盘

阅读级别：进阶。原报告首次：2.6.3 复杂度与规模估算；PDF 第 11 页。

**怎么理解：** 内存是程序运行中使用的工作区，磁盘用于较长期保存。flush 将语言层缓冲的数据交给后续写入层；fsync 请求操作系统同步文件数据到存储设备。

**放进本项目：** 保存临时索引时依次 flush、fsync，再替换正式路径，尽量减少尚未写好的文件被启用。

**容易误解：** 不能把一次文件 fsync 当作所有设备和断电场景的绝对保证。可靠恢复还涉及文件系统、目录更新和备份。

## 080 事务式更新、提交与回滚思路

阅读级别：查阅。原报告首次：2.7.1 增量导入的更新顺序；PDF 第 12 页。

**怎么理解：** 把多步修改当作一次有边界的更新：准备阶段出错时保留旧状态，达到提交点才启用新状态。“回滚”泛指恢复到更新前状态。

**放进本项目：** 本项目通过候选索引加成功保存后切换，减少失败导入对现有库的影响。

**容易误解：** 这里不是完整数据库事务。文件替换、内存切换、突然断电和多写者之间仍有需要单独处理的边界。

## 081 NPZ 与 knowledge.npz

阅读级别：查阅。原报告首次：2.7.2 NPZ 文件中保存什么；PDF 第 12 页。

**怎么理解：** NPZ 是把多个 NumPy 数组打包保存的一种文件格式，可以理解为装了若干数组的容器。它不是一种向量算法。

**放进本项目：** 项目保存序列化的 FAISS 字节，以及装有原文、元数据和配置的 JSON 数据。

**容易误解：** 扩展名不提供加密或可信证明。这个文件包含可读资料内容，只应按当前设计读取可信来源、由程序自身生成的索引。

## 082 序列化、反序列化与 pickle

阅读级别：查阅。原报告首次：2.7.2 NPZ 文件中保存什么；PDF 第 12 页。

**怎么理解：** 序列化把内存中的结构变成能保存或传输的表示；反序列化再把它恢复。pickle 是 Python 的一种对象序列化机制。

**放进本项目：** FAISS 索引被转换为字节；原文与元数据用 JSON。np.load 设置 allow_pickle=False，避免按 pickle 恢复对象。

**容易误解：** 不用 pickle 只减少一类风险，不等于整个索引加载流程可接受任意恶意文件；原生解析和资源耗尽仍需考虑。

## 083 JSON

## 099 MRR（平均倒数排名）

阅读级别：查阅。原报告首次：3.4 效果评价方案；PDF 第 19 页。

**放进本项目：** 三题首个相关结果分别排第 1、第 2 和未命中，平均为 (1+1/2+0)/3=0.5。

**容易误解：** MRR 主要看第一条相关结果出现得早不早，不直接衡量后续所有证据的覆盖程度。

# 用例子把关键方法串起来

## 例一：一个问题经过系统后到底发生什么

问题是：“为什么要同时归一化文档向量和查询向量？”资料 A 写“两个向量都归一化后，内积等于余弦相似度”；资料 B 写“Streamlit 用来制作页面”。

1. 上传时，程序先把资料 A、B 读成文字片段，并给每段加上文件名和页码等信息。
2. Embedding 把两个片段编码为同维向量；程序归一化后写入 FAISS，同时保留对应原文。
3. 提问时，当前问题也用同一个模型编码并归一化。
4. FAISS 比较查询与各片段，返回向量位置和分数；项目按位置找到资料 A 的正文与出处。
5. 若 A 通过阈值与上下文预算筛选，Prompt 把 A、问题和规则一起交给问答模型。
6. 问答模型逐步返回文字，界面显示回答和 A 的原文。你检查结论是否确实由 A 支持。

注意：模型没有在每次提问时重新读所有原始 PDF，也没有因为导入资料就被重新训练。离线模式到最后一步时直接摘录原文，不调用问答模型。

## 例二：亲手算一次归一化、内积和余弦

为了算得清楚，下面只使用二维教学向量。它们不是项目真实模型的输出，也不是“第一维就是某主题”的解释。

查询 q=[3,4]。sqrt 表示求平方根，也就是开平方。长度为 sqrt(3²+4²)=sqrt(25)=5，所以归一化后 q_unit=[0.6,0.8]。

候选 A=[6,8]，长度为 10，归一化后也是 [0.6,0.8]。它与 q 的原始内积是 50；原始余弦是 50/(5×10)=1；单位向量内积是 0.6²+0.8²=1。

候选 B=[4,3]，长度为 5，归一化后为 [0.8,0.6]。它与 q 的单位向量内积是 0.6×0.8+0.8×0.6=0.96。

候选 C=[-4,3]，长度为 5，归一化后为 [-0.8,0.6]。它与 q 的单位向量内积是 -0.48+0.48=0。

| 候选 | 原始向量 | 原始内积 | 归一化后内积，即余弦 |
| --- | --- | --- | --- |
| A | [6,8] | 50 | 1.00 |
| B | [4,3] | 24 | 0.96 |
| C | [-4,3] | 0 | 0.00 |

A 的长度比 q 大，但方向相同；余弦不因它只是按比例变长而增加。这个例子说明归一化在数学上做了什么，不说明文本语义质量如何。零向量没有可用于这个公式的方向，不能直接除以其长度。

## 例三：分段为什么要重叠

原文说：“文档向量与查询向量必须都做 L2 归一化。满足这个条件后，内积才等于余弦相似度。”如果第一句在片段 A、第二句在片段 B，系统只取回 B 时，模型可能漏掉成立条件。

重叠让边界附近的部分文字同时出现在两段里，增加条件与结论一起被找到的机会。但两段太相似，也可能同时占据 Top-K。重叠是在完整性、数量、费用与重复之间做取舍，并非越大越好。

调参顺序建议是：先确认原文抽取正确，再检查关键知识是否被切断，然后调整分隔符或长度，最后观察检索与回答变化。不能用无限增大 K 代替修复坏文本。

## 例四：Top-K、阈值和上下文预算不是同一个开关

设 5 个候选按分数从高到低为 A=0.82、B=0.61、C=0.31、D=0.08、E=0.02。

1. Top-K=4：最多先取 A、B、C、D，不取 E。
2. 最低相似度=0.20：去掉 D，剩 A、B、C。
3. 假设一个教学用上下文预算，计入标题与分隔符后仅够放完 A、B 及 C 的一部分：C 可能被截断；若剩余预算不足以形成可用来源，则不加入 C。
4. 页面应显示实际送入模型的文本，不能展示完整 C 来让用户误以为模型看到了全部。

K 管条数，阈值管分数，预算管总篇幅。调整聊天模型，不会自动改变已存文档向量；改变向量模型，则通常应重建。

## 例五：用很小的题集区分三个检索指标

假设每题的相关证据已经由人标好，评价前固定“什么算一条证据”。表中的排名都在检查范围内，题 C 未命中。

| 问题 | 全部相关证据数 | 前 4 条找回数 | 首条相关排名 |
| --- | --- | --- | --- |
| A | 2 | 2 | 1 |
| B | 3 | 1 | 3 |
| C | 1 | 0 | 无 |

Hit@4=(1+1+0)/3=2/3，表示三题中两题至少命中一条。

按题平均的 Recall@4=(2/2+1/3+0/1)/3=4/9，约 44.4%。注意这不同于把全表计数先加总再除的 3/6=50%；二者采用不同汇总口径，报告时不能混用。

MRR@4=(1/1+1/3+0)/3=4/9，约 0.444。这里恰好与上式数值相同只是这个例子的巧合；MRR 看的是首个相关排名，Recall 看的是证据覆盖。

这些仍是检索指标。就算三题都找到资料，模型也可能读错或引用错。因此还需逐条核对回答是否受资料支持。本例是教学计算，不是本项目真实质量评测结果。

## 例六：两套 API 配置应该怎么想

向量侧的职责是“把文本变成数值”；问答侧的职责是“把问题和资料组织成答案”。每一侧都有自己的服务地址、密钥和模型名。

| 现象 | 优先排查哪条链路 | 为什么 |
| --- | --- | --- |
| 文档导入时失败 | 文档处理及向量侧配置 | 此时通常还没有调用问答模型 |
| 文档导入成功，提问编码失败 | 查询向量侧 | 文档和查询仍需同一套编码规则 |
| 检索和来源正常，但生成失败 | 问答侧、网络及响应解析 | 找到资料与成功生成是两步 |
| 回答流畅但内容不对 | 原文、分段、检索、上下文及生成 | 技术连通与内容正确不是同一问题 |

先定位失败阶段，再改对应设置。不要因为问答侧密钥丢失就重新给全部资料生成向量；也不要因为返回 400 就假定所有问题都能靠减小批量解决。
